# ADMITWISE — Academic Admission Planner

واجهة محلية لتنظيم شروط القبول الجامعي ومقارنتها بالملف الأكاديمي للطالب، مع تفسير سبب كل نتيجة.

> **الحالة:** نموذج أولي MVP. لا توجد بيانات قبول حقيقية مرفقة؛ يضيف المستخدم المؤسسات وشروطها يدويًا مع مصدرها وسنة القبول.

## نطاق المنتج المعتمد

راجع مواصفات المنتج والهندسة في [docs/PRODUCT_SPEC.md](docs/PRODUCT_SPEC.md). أضيفت طبقة اكتشاف أولية تتضمن قاموس تخصصات ومؤسسات متعدد اللغات، وفرض اختيار 1–5 مؤسسات، وحفظ نطاق البحث محليًا. البحث المباشر عن صفحات المؤسسات واستخراج الشروط لم يُفعّل بعد ويتطلب موصل بحث خادميًا وقائمة نطاقات رسمية موثقة.

## الفكرة الأساسية

- استبيان إعداد أولي يحدد التخصص والدرجة وسنة البدء والمنطقة ولغة الدراسة.
- ملف أكاديمي يدوي للبجروت والبسيخومتري وامتحانات اللغة.
- سجل لكل مؤسسة وبرنامج وسنة قبول، مع رابط المصدر وتاريخ مراجعته.
- محرر قواعد يدعم مجموعات `AND` للشروط الإلزامية ومجموعات `OR` للبدائل.
- مقارنة تفسيرية بثلاث حالات: مستوفى، غير مستوفى، ومعلومات ناقصة.
- نسخ احتياطي واستعادة عبر JSON.
- PWA مبدئية مع تخزين غلاف التطبيق للعمل دون اتصال بعد أول زيارة.
- شاشة «مختبر البحث» لتوثيق سؤال البحث والمنهجية ومؤشرات جودة السجلات.

## الخصوصية والتخزين

- لا يوجد تسجيل دخول، ولا قاعدة بيانات، ولا تحليلات أو خدمات تتبع.
- العلامات، التفضيلات، وسجلات المؤسسات تُحفظ في `IndexedDB` داخل المتصفح.
- محرك المقارنة يعمل داخل JavaScript في المتصفح. لا توجد نقطة API تستقبل الملف الأكاديمي.
- خادم Flask يقدم صفحة التطبيق ونقطة `/health` غير الحساسة فقط.
- تصدير JSON ينشئ نسخة على جهاز المستخدم؛ يجب حفظها في مكان آمن.
- مزود الاستضافة (Vercel) قد يعالج بيانات الاتصال التقنية المعتادة لطلب الصفحة، مثل عنوان IP ووقت الطلب؛ لا يرسل التطبيق إليه العلامات أو سجل المؤسسات أو ملف النسخ الاحتياطية.
- التخزين مرتبط بالمتصفح والجهاز. حذف بيانات الموقع أو استخدام متصفح/جهاز آخر لا ينقل البيانات تلقائيًا.

**تنبيه:** الموقع المنشور على الإنترنت يمكن الوصول إلى شيفرته العامة، لكن ذلك لا يمنح الخادم الوصول إلى بيانات IndexedDB. تبقى بيانات المستخدم محلية ما دام التطبيق لا يضيف لاحقًا ميزة مزامنة أو إرسال بيانات.

## البنية التقنية

- Python 3.11+ وFlask لتقديم واجهة التطبيق محليًا وعلى Vercel.
- HTML وCSS وJavaScript ES modules للواجهة ومحرك القواعد المحلي.
- IndexedDB للتخزين الهيكلي.
- Service Worker لتخزين ملفات الواجهة مؤقتًا للاستخدام دون اتصال.
- `tools/validate_backup.py` للتحقق من ملف النسخة الاحتياطية محليًا دون رفعه.

## النشر على Vercel

Vercel يدعم Flask ضمن Python runtime. بعد إنشاء مستودع GitHub وربطه بمشروع Vercel:

1. ادفع الملفات إلى فرع `main`.
2. اربط المستودع بمشروع Vercel واختر Python/Flask أو اترك الكشف التلقائي.
3. لا تضف متغيرات بيئة أو قاعدة بيانات؛ لا يحتاج التطبيق إلى أسرار أو تخزين سحابي.
4. اختبر رابط Preview قبل اعتماد Production.
5. تأكد من أن ملفات `public/` تُخدم من CDN وأن `/health` يعيد `status: ok`.

## كيف لا نضلل الطالب؟

- عبارة «يستوفي الشروط المسجلة» لا تعني «مقبول».
- أي خانة أكاديمية فارغة ينتج عنها «غير محسوم» بدل اعتبارها رسوبًا.
- لا تُحسب نسبة احتمالية للقبول؛ لا توجد بيانات إحصائية تبرر ذلك.
- يجب إدخال سنة القبول ومصدر رسمي وتاريخ مراجعة لكل برنامج.
- المعدل الموزون للبجروت يُدخل كما حسبته المؤسسة؛ لا نفترض أن كل المؤسسات تستخدم طريقة واحدة.

## تحويله إلى مشروع بحثي

**سؤال بحث مقترح:** هل يساعد نظام محلي قابل للتفسير في تقليل وقت وأخطاء مقارنة شروط القبول لدى الطلاب؟

**تصميم الدراسة:** منهج Design Science Research؛ تصميم الأداة ثم اختبارها بحالات اصطناعية موثقة ومقارنة نتائجها بمخرجات مرجعية يدوية.

**متغيرات التقييم:**

1. دقة تنفيذ القواعد (مطابقة حالات الاختبار المرجعية).
2. زمن الوصول إلى تقييم برنامج أكاديمي.
3. نسبة شروط القبول التي لها مصدر وتاريخ مراجعة.
4. قدرة الطالب على شرح سبب ظهور كل حالة.
5. قابلية الاستخدام باستبيان قصير بعد تجربة مهام محددة.

لا تجمع الدراسة علامات حقيقية أو بيانات تعريفية ما لم توجد ضرورة وموافقة وإجراءات أخلاقية مناسبة؛ يمكن تنفيذ الاختبار بملفات اصطناعية.

## حدود الإصدار الأول

- إدخال شروط القبول يدويًا؛ لا يوجد سحب آلي من مواقع الجامعات.
- لا يوجد حساب تلقائي للمعدل الموزون الخاص بكل مؤسسة.
- لا يوجد تنبؤ إحصائي بفرصة القبول.
- لا يوجد مزامنة بين الأجهزة أو استرجاع عند فقدان الجهاز دون النسخة الاحتياطية.
- الاستبيان يحفظ التفضيلات، لكنه لا يقرر الأهلية أو يوصي بمؤسسة دون شروط موثقة.
